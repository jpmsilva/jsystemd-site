Status providers

The status of a service is the line that systemctl status shows, sent by the application to systemd. A status provider contributes a part of it, implementing StatusProvider: the status is made of the parts of all the status providers registered in the Systemd instance, in their order, separated by commas. A status provider with nothing to report returns an empty string, and is left out. If no status provider is registered at all, no status is sent to systemd.

[root@machine ~]# systemctl status myservice.service
● myservice.service - My Service
   Loaded: loaded (/etc/systemd/system/myservice.service; disabled; vendor preset: disabled)
   Active: active (running) since Qui 2018-02-15 10:19:28 WET; 1h 24min ago
 Main PID: 11142 (java)
   Status: "Heap: 139.5 MiB/256.0 MiB, Non-heap: 62.7 MiB/64.1 MiB, Classes: 7915, Threads: 31 (9 runnable; 14 waiting; 8 timed waiting)"
   CGroup: /system.slice/myservice.service
           └─11142 /opt/jdk17/bin/java -XX:+ExitOnOutOfMemoryError -jar /opt/myservice/myservice.jar

The core library provides status providers for the JVM, which any application can use. The integrations with Spring Boot and Keycloak register them for the application, along with status providers of their own.

Core library

Registering status providers

Register status providers with addStatusProviders(…) on the Systemd instance of the process, returned by Systemd.instance(), and remove them with removeStatusProviders(…). Their parts are shown in the order they were registered, unless added at a given position.

The status is sent to systemd periodically once enabled with enableStatusUpdate(period), and right away with updateStatus(), such as at each milestone of a long startup:

Systemd systemd = Systemd.instance();
systemd.addStatusProviders(new HeapStatusProvider(), new NonHeapStatusProvider(), new ClassLoaderStatusProvider(),
    new ThreadStatusProvider(false, false));
systemd.enableStatusUpdate(Duration.ofSeconds(5));

See How to for the full lifecycle, with a complete example.

Most of them are created without arguments. The others are configured when created:

  • the ThreadStatusProvider can also detect deadlocked threads, adding their number to the status, such as 2 deadlocked, when created with new ThreadStatusProvider(true, false);
  • the FileDescriptorStatusProvider shows the open file descriptors out of the most the process can open, the LimitNOFILE of the service unit, and is created with the share of that limit from which it reports the application as unhealthy, such as new FileDescriptorStatusProvider(false, 0.9);
  • the CgroupTasksStatusProvider shows the tasks of the service, its processes and their threads, out of the most it can have, the TasksMax of the service unit, and is created with the share of that limit from which it reports the application as unhealthy, such as new CgroupTasksStatusProvider(false, 0.9);
  • the GarbageCollectionStatusProvider can also be created with the share of the time taken by the pauses from which it reports the application as unhealthy, such as new GarbageCollectionStatusProvider(true, 0.5);
  • the ExecutorStatusProvider is created with the name to show and the ThreadPoolExecutor to report, or a supplier of it, for a pool created later;
  • the PhaseStatusProvider shows nothing until the application sets a phase. When created with new PhaseStatusProvider(true), every change of phase is sent to systemd right away, rather than with the next status update.

The ThreadStatusProvider, the FileDescriptorStatusProvider, the CgroupTasksStatusProvider and the GarbageCollectionStatusProvider can also report the application health, to restart it on deadlocks, when its file descriptors or its tasks are about to run out, or while it spends most of its time collecting garbage. Registering them as status providers only adds them to the status: see Health providers to have their health taken into account.

Some of them only have something to report in some environments, and report nothing elsewhere:

  • the VirtualThreadStatusProvider shows the virtual threads that are running, each mounted on a platform thread of their scheduler, and those that are ready to run but wait for one. It complements the ThreadStatusProvider, which only sees platform threads: virtual threads that keep waiting while every platform thread of the scheduler has one mounted are held back, by more work than the CPUs can take, or by virtual threads that block without giving up their platform thread. The scheduler can only be observed on Java 24 and later;
  • the CgroupMemoryStatusProvider, the CgroupPressureStatusProvider and the CgroupTasksStatusProvider read the control group of the service, in the unified hierarchy (cgroup v2), which systemd uses on current Linux distributions.

The CgroupPressureStatusProvider shows how much the service is held back by a lack of resources, which neither its CPU usage nor its memory usage tell:

  • the pressure of the CPU, the memory and the I/O is the share of the last 10 seconds in which at least one task of the service was stalled waiting for it, as the kernel measures it (pressure stall information): runnable but waiting for a CPU, reclaiming memory, or waiting for I/O. Memory pressure that keeps growing means the service is about to reach its MemoryHigh or MemoryMax, even though its heap may still have room;
  • the throttling is the share of the enforcement periods of the CPU quota of the service, since the status was last read, in which the service used up its quota, and was kept from running until the next one. It is only shown when the service has a quota, the CPUQuota of the service unit: a throttled service is slow while the system has idle CPUs.

Each part is left out when the kernel does not report it.

Reporting what the application is doing

To report what the application is doing without writing a status provider, register a PhaseStatusProvider and set its phase:

PhaseStatusProvider phase = new PhaseStatusProvider(true);
Systemd.instance().addStatusProviders(phase);

phase.setPhase("Reindexing");
try {
  // ...
} finally {
  phase.clearPhase();
}

Custom status providers

You can create your own status information by implementing StatusProvider, and registering an instance with addStatusProviders(…):

public class QueueStatusProvider implements StatusProvider {

  private final Queue<?> queue;

  public QueueStatusProvider(Queue<?> queue) {
    this.queue = queue;
  }

  @Override
  public String status() {
    return "Queue: " + queue.size();
  }
}

The status is asked for on every status update, from the thread that sends it: keep it quick, and return an empty string when there is nothing to report. A status provider only reports the status: it must not drive the lifecycle of the application, by calling ready(), stopping() or close() on the Systemd instance.

Reporting only in some states of the application

A status provider is asked for its status in every state of the application: while it starts up, while it runs, and while it stops. To only report in some of them, a status provider implements the matching interfaces, one or more of:

  • StartingStatusProvider, until the application is ready (ready());
  • RunningStatusProvider, once ready, until the application is stopping (stopping());
  • StoppingStatusProvider, once the application is stopping, including when it stops before it is ready.

In the other states, the status provider is not even asked for its status. This suits status providers whose status means nothing in some states, such as the progress of the startup, or whose sources may not be available, such as the health of a remote service, checked with a connection pool that is closed once the application stops:

public class QueueStatusProvider implements RunningStatusProvider {
  // ...
}

Under Spring Boot

When using the autoconfiguration class, the built-in status providers are registered for the application, and StatusProvider beans will also be searched in the application context and used to compose an extended status message that systemd will display when using the status verb. The status is sent to systemd once every five seconds, or at the period set with systemd.status-update-period, such as 30s, to call the status providers less often, such as Actuator health indicators that query remote services.

Out of the box this module will show memory (heap, old generation, non-heap, buffers and the memory of the control group of the service), classloader information, threads, file descriptors, the availability of the application, application startup sequence state and bean creation progress, the stage of the shutdown, as well as the application health when using Spring Boot Actuator. The garbage collection pauses, the CPU usage, the virtual threads, and the pressure and the tasks of the control group of the service can be shown as well, once enabled.

Additionally, the status of the libraries the application uses is shown when they are available: the connections of the embedded web server (Tomcat, Jetty or Reactor Netty), the HikariCP connection pools, the thread pools of the task executors and schedulers, the message listener containers (Kafka, RabbitMQ and JMS), and the progress of the Liquibase and Flyway database migrations run on startup. The R2DBC connection pools, the scheduled tasks, chosen Micrometer meters and the version of the application can be shown as well, once enabled.

The scheduled tasks of the application, the values of chosen Micrometer meters and the version of the application can be shown as well, once enabled.

[root@machine ~]# systemctl status myservice.service
● myservice.service - My Spring Boot Service
   Loaded: loaded (/etc/systemd/system/myservice.service; disabled; vendor preset: disabled)
   Active: active (running) since Qui 2018-02-15 10:19:28 WET; 1h 24min ago
 Main PID: 11142 (java)
   Status: "health status: healthy, Liveness: correct; readiness: accepting traffic, Heap: 139.5 MiB/256.0 MiB, Old gen after GC: 48.2 MiB/256.0 MiB, Cgroup memory: 310.4 MiB, Threads: 31 (9 runnable; 14 waiting; 8 timed waiting), File descriptors: 64/524288, http-nio-8080: 8/8192 connections, 3/10 threads, Non-heap: 62.7 MiB/64.1 MiB, Buffers: 1.2 MiB/256.0 MiB direct (14), Classes: 7915"
   CGroup: /system.slice/myservice.service

Configuring status providers

Some status providers have settings of their own, next to enabled, under the same systemd.status-providers.<key>.

threads

The threads status provider shows the number of threads by state, such as Threads: 31 (9 runnable; 14 waiting; 8 timed waiting). It can also detect deadlocked threads, once opted into: their number is added to the status, such as 2 deadlocked. It is also a health provider, which can restart the application on deadlocks (see Health providers).

Property Default Description
systemd.status-providers.threads.deadlock-detection false Detect deadlocked threads, and report them in the status.

virtual-threads

The virtual-threads status provider is opted into, with systemd.status-providers.virtual-threads.enabled=true. It shows the virtual threads that are running, each mounted on a platform thread of their scheduler, those that are ready to run but wait for one, and the platform threads the scheduler has, such as Virtual threads: 8 mounted; 340 queued; 8 carrier threads. Virtual threads that are blocked, waiting or sleeping are not counted.

With virtual threads (spring.threads.virtual.enabled=true), the requests and the tasks of the application are not handled by thread pools, so the tomcat, jetty and task-executors status providers show no threads, and the threads one only sees platform threads. Virtual threads that keep waiting while every platform thread of the scheduler has one mounted are held back, by more work than the CPUs can take, or by virtual threads that block without giving up their platform thread. The scheduler can only be observed on Java 24 and later: nothing is shown on earlier versions.

file-descriptors

The file-descriptors status provider shows the open file descriptors out of the most the process can open, the LimitNOFILE of the service unit, such as File descriptors: 812/65536. It is also a health provider, which can restart the application when the file descriptors are about to run out (see Health providers).

cgroup-tasks

The cgroup-tasks status provider is opted into, with systemd.status-providers.cgroup-tasks.enabled=true. It shows the tasks of the service, its processes and their threads, out of the most it can have, the TasksMax of the service unit, such as Cgroup tasks: 312/4915. It is also a health provider, which can restart the application when the tasks are about to run out, as the JVM can then no longer create threads (see Health providers).

cgroup-pressure

The cgroup-pressure status provider is opted into, with systemd.status-providers.cgroup-pressure.enabled=true. It shows how much the service is held back by a lack of CPU, memory or I/O, and how often it runs out of its CPUQuota, such as Cgroup pressure: 2.1% cpu; 0.0% memory; 12.3% io; 40.0% throttled (see Built-in status providers).

garbage-collection

The garbage-collection status provider is opted into, with systemd.status-providers.garbage-collection.enabled=true. It shows the garbage collection pauses since the status was last sent, and the share of the time they took, such as GC: 12 pauses, 0.4% of time. It is also a health provider, which can restart the application while it spends most of its time collecting garbage, as it does when it is about to run out of heap (see Health providers).

tomcat

The tomcat status provider shows the usage of each connector of the embedded Tomcat:

  • the open connections, out of the maximum the connector accepts (server.tomcat.max-connections, 8192 by default), which includes idle keep-alive connections;
  • when the requests are handled by a thread pool, the busy threads, out of the threads in the pool.

So, http-nio-8080: 8/8192 connections, 3/10 threads means that the http-nio-8080 connector has 8 open connections, out of the 8192 it accepts, and that 3 of the 10 threads of its pool are serving requests.

With virtual threads (spring.threads.virtual.enabled=true), the requests are not handled by a thread pool, so only the connections are shown, such as http-nio-8080: 8/8192 connections. When the connector accepts unlimited connections (server.tomcat.max-connections=-1), Tomcat does not count them, so only the threads are shown, such as http-nio-8080: 3/10 threads.

When the management endpoints use a port of their own (management.server.port), the connector of their server is shown as well. The connectors are read directly from the embedded Tomcat, so the Tomcat MBeans do not need to be enabled (server.tomcat.mbeanregistry.enabled).

It is also a health provider, which can restart the application while a connector is saturated, with all its threads busy and requests waiting for one, which usually means that its requests hang (see Health providers).

jetty

The jetty status provider shows the usage of each embedded Jetty server, named after the ports it listens on, such as jetty-8080, or jetty-8080+8443 for a server with several connectors:

  • the open connections of all its connectors together, out of the maximum the server accepts when limited (server.jetty.max-connections, unlimited by default);
  • when the requests are handled by a thread pool, the threads running requests, out of the threads in the pool. The threads Jetty keeps for itself, to accept connections and wait for their data, never run requests, and are left out of both.

So, jetty-8080: 12/1000 connections, 3/10 threads means that the server has 12 open connections, out of the 1000 it accepts, and that 3 of the 10 threads of its pool that can run requests are running one. Without a limit of connections, only their number is shown, such as jetty-8080: 12 connections, 3/10 threads. With virtual threads (spring.threads.virtual.enabled=true), the requests are not handled by a thread pool, so only the connections are shown.

When the management endpoints use a port of their own (management.server.port), their server is shown as well. A server is only shown once it listens.

It is also a health provider, which can restart the application while a server is saturated, with all its threads taken and requests waiting for one, which usually means that its requests hang (see Health providers).

netty

The netty status provider shows the usage of each embedded Reactor Netty server, as used by Spring WebFlux, named after the port it listens on: the open connections and the requests being handled, such as netty-8080: 12 connections, 3 requests. Reactor Netty handles requests on a few event loop threads, which never block, so there is no thread pool to report on, nor a maximum of connections.

Reactor Netty does not count its connections and requests unless it records metrics with Micrometer, so the status provider counts them itself, by customizing the servers Spring Boot creates: disabling it also stops counting them. When the management endpoints use a port of their own (management.server.port), their server is shown as well. A server is only shown once it listens.

hikari

The hikari status provider requires HikariCP, the connection pool Spring Boot uses by default. For each pool, named after its data source bean, it shows the connections in use out of the most the pool opens, and the threads waiting for a connection, such as dataSource: 7/10 connections, 3 waiting. A pool is only shown once started, which Hikari does on the first connection.

It is also a health provider, which can restart the application while a pool is starved, which usually means that connections leak (see Health providers).

task-executors

The task-executors status provider shows the thread pools of the task executors and schedulers of the application, the ThreadPoolTaskExecutor and ThreadPoolTaskScheduler beans, such as the ones Spring Boot sets up for @Async and @Scheduled methods. Each is named after its bean, and shows the busy threads out of the threads in the pool, and the tasks waiting for a thread, such as applicationTaskExecutor: 2/8 threads, 5 queued. For a scheduler, the tasks waiting are those scheduled to run, including the periodic ones between their runs, such as taskScheduler: 1/1 threads, 3 scheduled.

The threads in the pool are those it has created so far, not its maximum: a pool creates its threads as tasks arrive, so an idle one may show 0/0 threads. The beans are found once all singleton beans are created, so that lazy ones are not created for the status. With virtual threads (spring.threads.virtual.enabled=true), Spring Boot sets up task executors and schedulers without a thread pool, which are left out.

To show the thread pool of an executor that is not one of these beans, register an ExecutorStatusProvider for it (see Built-in status providers).

scheduled-tasks

The scheduled-tasks status provider shows the scheduled tasks of the application, such as its @Scheduled methods: how many there are, how many are running, and how many failed the last time they ran, such as Scheduled tasks: 5 (1 running; 1 failing). It is disabled by default:

systemd.status-providers.scheduled-tasks.enabled=true

A scheduled task that fails only logs its failure, and runs again when it is next due, so a task that fails every time is easily missed. A task is shown as failing from its failure until it next runs, and again if that run fails too; while it runs, it is shown as running, whatever the outcome of its previous run. While no task is running nor failing, only their number is shown, such as Scheduled tasks: 5, and nothing is shown for an application without scheduled tasks.

The tasks are those that Spring schedules for the application, the same as the scheduledtasks endpoint of Spring Boot Actuator shows, including those registered with a SchedulingConfigurer. Tasks that the application schedules itself, directly on a TaskScheduler, are not known to Spring, and are left out. The tasks are only shown while the application runs, as they are cancelled once it stops.

micrometer

The micrometer status provider requires Micrometer, which Spring Boot Actuator sets up. It shows the values of the meters it is configured with, so that the application can show what its libraries measure, such as its caches, its message listeners or its HTTP clients, without writing a status provider for each of them. It is disabled by default, and shows nothing until it is given the meters to show:

systemd.status-providers.micrometer.enabled=true
systemd.status-providers.micrometer.meters[0].name=hikaricp.connections.active
systemd.status-providers.micrometer.meters[1].name=http.server.requests
systemd.status-providers.micrometer.meters[1].tags.outcome=SERVER_ERROR
systemd.status-providers.micrometer.meters[1].label=Failed requests

This shows hikaricp.connections.active: 7, Failed requests: 12. Each meter to show has:

Property Default Description
name The name of the meter, as the metrics endpoint of Spring Boot Actuator lists them. Required: without it, the application fails to start.
tags not set The tags the meter must have, by key, to narrow the meters with the name. Without tags, all of them are taken into account.
label not set The label the value is shown under, instead of the name of the meter.

The value is the one the metrics endpoint shows for the same name and tags (/actuator/metrics/<name>?tag=<key>:<value>), whether or not the endpoint is exposed: a name usually has a meter for each combination of its tags, and the measurements of all those that match are added together. What is shown depends on the type of the meter:

  • gauges show their value;
  • counters show their count;
  • timers and distribution summaries show how many times they recorded, such as the requests handled, not the times or the amounts recorded;
  • long task timers show the tasks that are running.

A meter that does not exist is left out, rather than being an error, as most meters are only registered once what they measure is first used. The meters are shown in the order they are configured in. Whole numbers are shown as they are, and the others rounded to two decimal places; from a million on, numbers are shortened, such as 1.5M, 2.3G or 4T, and values measured in bytes are shown as the memory status providers show them, such as 133.2 MiB.

The meters are read from the meter registry of the application, the primary one when there are several, as the one Spring Boot sets up. Without one, a warning is logged, and the meters are looked up in the global registry of Micrometer, which only has the meters that libraries register there themselves.

version

The version status provider shows the version of the application that is running, from the build information that Spring Boot exposes: the version of the build, followed by the short id of the commit it was built from, such as Version: 1.4.2 (a1b2c3d). It is disabled by default:

systemd.status-providers.version.enabled=true

The version comes from META-INF/build-info.properties, which the build-info goal of the Spring Boot Maven plugin generates, as does the buildInfo() task of its Gradle plugin, and the commit from git.properties, which the Git commit id plugins of Maven and Gradle generate. These are the same as the info endpoint of Spring Boot Actuator shows, which is not needed. With only one of them, only the version, or only the commit, is shown, and nothing is shown for an application built without both.

availability

The availability status provider shows the liveness and readiness of the application, as Spring Boot reports them, such as Liveness: correct; readiness: accepting traffic. It is also a health provider, which can restart the application while its liveness state is broken (see Health providers).

liquibase

The liquibase status provider requires Liquibase. It shows the progress of the database migrations run on startup by the SpringLiquibase beans, such as the one Spring Boot sets up, as each changeset is applied, such as Liquibase: applying changeset 042-add-index (41 applied). It is cleared once the migrations complete, and when they fail, the changeset that failed is still shown while the application fails to start.

Each changeset also extends the startup timeout (see Startup and shutdown timeouts), so that a migration with many changesets does not exceed the TimeoutStartSec of the service unit. A single changeset that takes longer than the extension still exceeds it: raise TimeoutStartSec for such a migration.

The changesets are reported through the customizer of the SpringLiquibase beans, which keeps the customizer they already have, such as a Customizer<Liquibase> bean of the application. A customizer that sets a ChangeExecListener of its own replaces the one of this provider, in which case only the start of the migrations is shown.

flyway

The flyway status provider requires Flyway, and the support of Spring Boot for it (spring-boot-flyway). It shows the progress of the database migrations run on startup by the Flyway that Spring Boot sets up, as each migration is applied, such as Flyway: applying migration 42 add index (41 applied), with the version and the description of the migration, as in the name of its script, or the description alone for a repeatable migration. It is cleared once the migrations complete, and when they fail, the migration that failed is still shown while the application fails to start.

Each migration also extends the startup timeout (see Startup and shutdown timeouts), so that many migrations do not exceed the TimeoutStartSec of the service unit. A single migration that takes longer than the extension still exceeds it: raise TimeoutStartSec for such a migration.

The migrations are reported by a Callback that a FlywayConfigurationCustomizer adds to the configuration of Flyway, next to the callbacks it already has, such as the Callback beans of the application. It is the last of the customizers to run, unless they are ordered otherwise: a customizer that runs after it and sets the callbacks replaces the one of this provider, in which case the migrations are not shown. Neither are those of a Flyway that the application creates itself, which Spring Boot does not customize.

kafka-listeners

The kafka-listeners status provider requires Spring for Apache Kafka. It shows the Kafka listener containers of the application, those of its @KafkaListener methods and the MessageListenerContainer beans: how many of them run, out of those there are, the partitions assigned to those that run, and how many are paused, if any, such as Kafka listeners: 3/3 running, 12 partitions, 1 paused. Nothing is shown while there are none.

Only what the containers already know is shown, without asking the brokers, so the lag of the consumers is not. Containers that are never started, such as those of listeners with autoStartup = "false", are counted among those there are.

It is also a health provider, which can restart the application while a container stopped by itself, such as when it is not authorized (see Health providers).

rabbit-listeners

The rabbit-listeners status provider requires Spring AMQP. It shows the RabbitMQ listener containers of the application, those of its @RabbitListener methods and the MessageListenerContainer beans: how many of them run, out of those there are, and the active consumers of the simple containers (spring.rabbitmq.listener.type=simple, the default), such as RabbitMQ listeners: 2/2 running, 4 consumers. Nothing is shown while there are none.

The consumers drop to none while the broker cannot be reached, as the containers keep running, trying to start their consumers again. The direct containers do not tell how many consumers they have: without simple containers, only the containers are shown, such as RabbitMQ listeners: 2/2 running.

It is also a health provider, which can restart the application while a container stopped by itself, such as when its queues are missing (see Health providers).

jms-listeners

The jms-listeners status provider requires the JMS support of Spring (spring-jms). It shows the JMS listener containers of the application, those of its @JmsListener methods and the MessageListenerContainer beans: how many of them run, out of those there are, and how many are recovering their connection to the broker, if any, such as JMS listeners: 2/2 running, 1 recovering. A container keeps running while its broker cannot be reached, trying to connect again. Nothing is shown while there are none.

It is also a health provider, which can restart the application while a container stopped by itself, once it gives up connecting to the broker (see Health providers).

r2dbc

The r2dbc status provider requires r2dbc-pool, the connection pool Spring Boot uses for R2DBC, and is opted into, with systemd.status-providers.r2dbc.enabled=true. For each pool, named after its connection factory bean, it shows the connections in use out of the most the pool opens, and the subscribers waiting for a connection, such as connectionFactory: 7/10 connections, 3 waiting. A pool that is closed is left out.

It is also a health provider, which can restart the application while a pool is starved, which usually means that connections leak (see Health providers).

actuator-health

The actuator-health status provider requires Spring Boot Actuator. It shows the application health, as its health contributors report it, the same as the health endpoint (/actuator/health), with the same names, such as db, diskSpace, ping or redis.

It only names the unhealthy health contributors, such as health status: unhealthy (db, redis). Their details are left out, as they often contain sensitive information (error messages, host names, paths, …), and the status can be read by any local user, for instance with systemctl status, regardless of how Spring Boot Actuator exposes health details. The details are logged instead, when the watchdog heartbeat is suppressed.

It is also a health provider, which can restart the application while it is unhealthy. The status shows the health the watchdog takes into account, so the settings of the health provider, such as the health group whose members are taken into account, or the status codes considered as unhealthy, apply to the status as well (see Health providers).

The health is only shown while the application runs: while it starts up, the health contributors may depend on beans not created yet, and while it stops, on resources already closed, such as connection pools, whose health checks would fail and log their failures.

shutdown

The shutdown status provider shows the stage the application is at while it shuts down, so that a slow shutdown can be told apart from a hung one. It shows nothing until the application starts shutting down, and then follows the shutdown of the application context:

  1. Shutdown: stopping, once the context starts closing, while its life cycle beans stop, such as message listeners;
  2. Shutdown: waiting for active requests, while the embedded web server waits for the requests being handled to complete, when it shuts down gracefully, as it does by default (unless server.shutdown=immediate);
  3. Shutdown: destroying beans, once all life cycle beans are stopped, while the beans are destroyed, such as connection pools.

Every change of stage is sent to systemd right away. The status of the other status providers keeps being sent while the application shuts down, such as the connections of the web server, which drop as the requests complete, except for those that only report while the application starts up or runs, such as the application health (see Reporting only in some states of the application). See Startup and shutdown timeouts for how long systemd lets the shutdown take.

Custom status providers under Spring Boot

Custom status providers, written as described in Custom status providers, are registered by declaring them as beans in any configuration class:

@Configuration
@ConditionalOnSystemd
public class MyConfiguration {
  
  @Bean
  MyStatusProvider myStatusProvider() {
    return new MyStatusProvider();
  }
}

In the example above, the configuration class does not need to be annotated with ConditionalOnSystemd, because these beans are harmless even when not running under systemd. However, this way these extra resources do not have to be built at all. Check the Conditionals page for more information.

The status shows first the startup status providers (ApplicationRunStatusProvider and ApplicationContextStatusProvider), as well as any other status provider registered directly in the Systemd instance before the application context is refreshed, in the order they were registered. Then come the StatusProvider beans of the application context, in the order given by the @Order annotation of their bean methods or classes.

The built-in status provider beans are ordered by how useful their information is when operating a service in production, at least 200 apart, so that custom status providers can be placed between them. The critical ones, which tell whether the application is in trouble, use negative orders, and the others positive ones; 0 is left unused:

The LiquibaseStatusProvider and the FlywayStatusProvider are the exceptions: as they report the migrations run while the beans are created, they are registered directly in the Systemd instance as soon as they are created, right after the startup status providers.

To replace a built-in status provider, such as to configure it in a way its properties do not allow, declare a bean of its type: the built-in one is then left out, so that the status does not show the same information twice. Give it the order of the built-in one, from the table above, to keep its place in the status:

@Bean
@Order(-2000)
ThreadStatusProvider myThreadStatusProvider() {
  return new ThreadStatusProvider(true, true);
}

The LiquibaseStatusProvider and the FlywayStatusProvider cannot be replaced this way, as a bean of the application would not be registered as soon as it is created; disable them instead.

To report what the application is doing without writing a status provider, inject the PhaseStatusProvider bean and set its phase, which is sent to systemd right away. The bean only exists when running under systemd, so inject it as optional:

@Component
public class Reindexer {

  private final ObjectProvider<PhaseStatusProvider> phase;

  public Reindexer(ObjectProvider<PhaseStatusProvider> phase) {
    this.phase = phase;
  }

  public void reindex() {
    phase.ifAvailable(provider -> provider.setPhase("Reindexing"));
    try {
      // ...
    } finally {
      phase.ifAvailable(PhaseStatusProvider::clearPhase);
    }
  }
}

The Systemd instance can still be used directly, such as to send the status right away, with Systemd.instance().updateStatus().
